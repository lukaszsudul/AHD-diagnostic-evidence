# Case-result export identity repair

After the final XSim matrix finished `214/214`, the task-owned runner's CSV export inserted the observation dictionary for every result-field name. Since the simulator observation has no copy of the 13 preregistered stimulus/classification columns, those columns were empty in the first export. This was an output-join defect; the per-case execution and checker used the original `CASE_MATRIX.csv` row, and each XSim log retained its stimulus and `CASE_COMPLETE_<ID>` marker.

The original generated output is preserved privately as `private/CASE_RESULTS_UNJOINED.csv`, SHA-256 `C251D9078BD99A9732FC2165087F81F87BC9A1C887BBA73AA87EE8A39339672A`. A mechanical post-run join restored **only** the 13 columns from the frozen matrix, in exact row order. Before modifying the exported table it verified, for all 214 rows: consecutive matrix case ID, existing ACK mode consistency, exact `OBS` case/stimulus header, exact completion marker, and the simulator-log and pin-trace SHA-256 values already recorded in that row. Result, timing, pin, checker and outcome columns were not recomputed or changed. The joined `CASE_RESULTS.csv` SHA-256 is `D2C35E40E0B611CE9CB42A7278641879B558BB2269859E64131E6F16E0894D34`.

This is a transparent evidence export correction, **not** a fourth stimulus, model, RTL or checker revision and not a new simulation pass. The independent compliance audit consumed the joined table after the 214/214 identity/hash gate passed; its six deliberately corrupted-record negative tests passed. Both the original and joined file identities are reported so the repair cannot be mistaken for an unchanged first export.
